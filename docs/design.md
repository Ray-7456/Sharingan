# 设计说明

本文档记录 Sharingan 的核心设计决策。所有实现都应以本文档为准；与文档冲突的实现需要先修改文档。

## 1. 通道分工

一个重复性工作里的信息分两类，必须分开获取：

| 信息 | 例子 | 获取方式 |
|---|---|---|
| **意图**（为什么做、给谁、什么算好） | "做周报给专工看"、"异常值要修正为正常数据" | 录屏视频 + 语音讲解 + 澄清问答 |
| **规则**（精确的判定与计算） | 阈值 85/75/135；`T = ABS(H-I)`；回写只覆盖 A:O | **直接解析文件**（公式、条件格式、表头、命名区域）+ 澄清问答 |

结论：视频不是主要通道，只是意图通道。任何"只看视频就能生成工具"的路线在真实业务里都会失败（参考 VideoGUI 的结论：高层规划才是瓶颈）。

## 2. 流水线

```
采集 → 分析 → 澄清 → 生成 → 运行 → （异常）→ 交给 Agent 改规则 → 回归 → 新版本
```

### 2.1 分析阶段的产出（三件套）

1. **工作流说明（spec）**：输入文件、列映射、步骤、输出、频次。
2. **歧义清单（ambiguities）**：每条包含位置证据（时间点 / 单元格 / 截图）、当前猜测、候选答案。
3. **可行性分级**：
   - `scriptable`：规则明确，可直接脚本化（绝大多数数据搬运与阈值判定属于此类）；
   - `needs-rule`：能自动执行，但判据需要人给（例如"什么算异常、改成什么"）；
   - `attended`：不可逆或有责任风险，永远需要人确认（例如覆盖原始数据）；
   - `not-automatable`：需要专业判断且无稳定规则。

### 2.2 澄清阶段：两段式提问

- **第一段（录制前/录制中）**：结构化简表 —— 任务名、目的、频次、输入在哪、输出给谁、哪些步骤希望机器替代。建议录屏时开麦讲解，讲解内容天然携带意图。
- **第二段（分析后）**：带证据逐条提问。每个问题必须附上具体位置（"第 12 分钟你把 29.5 改成了 19.8，依据是什么？"），并给出候选选项，同时允许回答"不确定"和"每次都需人工确认"。

**提问只发生在构建期。** 用户第一次实际使用工具后的每一处手工修正，也必须被转化为规则（区分两类修改：改数据 = 一次性；改规则 = 持久化），否则下次运行同样的问题会再次出现。

## 3. 规则文件 rules.json

规则文件是唯一的运行期配置来源，人类可读、可改、可版本化。

```json
{
  "version": 3,
  "updated_at": "2026-07-24",
  "base_columns": ["A", "B", "C", "D", "E", "F", "G", "H", "I", "J", "K", "L", "M", "N", "O"],
  "columns": {
    "B": { "limit": 85, "source": "模板表头(85) vs 条件格式>=85，一致" }
  },
  "derived": {
    "T": { "formula": "abs(H-I)", "limit": 20,
           "source": "澄清#3：以表头(20)为准，模板条件格式中的 25 为笔误" }
  },
  "repair": {
    "B": { "action": "clip", "params": { "to": 84.9 }, "mode": "confirm-once",
           "source": "澄清#2：单点毛刺截断到限值以下" },
    "T": { "action": "clip", "params": { "target": "I", "to": 55 }, "mode": "confirm-once",
           "source": "澄清#3：温差超限时改原始测点 I，且 I 不应超过 55℃" }
  },
  "missing_data": {
    "备注=此时间点无数据": { "action": "keep_and_flag", "mode": "auto" }
  },
  "writeback": {
    "range": "A:O", "encoding": "gbk", "date_format": "%Y-%-m-%-d %-H:%M:%S",
    "preserve_columns": ["备注"], "backup": true,
    "overwrite": { "mode": "attended" }
  },
  "unmatched": { "mode": "halt" }
}
```

字段约定：

- `base_columns`（可省略）：输入列清单。给出时，派生列公式引用的列必须落在其中或另一个派生列里，否则校验报错。
- `repair`（以**被修改的列字母**为键，不在 `base_columns` / `derived` 中的键会报错）：

  | 动作 | 含义 | 必填参数 |
  |---|---|---|
  | `clip` | 新值 = min(旧值, params.to) | `to`（数值） |
  | `interpolate` | 用前后最近的未超限点按时间线性插值 | — |
  | `keep_and_flag` | 不改数值，把标注追加到备注列 | 可选 `note`（默认「超限」） |
  | `reject` | 明确决定"不改，交人工判断"——只登记，不算遗漏 | — |

  派生列超限时，若要在原始测点上动手，用 `params.target` 指定要改写的列
  （例如 `T` 超限时改 `I`）：工具不会反解公式，只按 `target` 列的规则改值。
  未指定 `target` 的派生列触发会记为「需人工判断」，不会被静默忽略。
- `mode` 三种取值：
  - `auto`：直接执行；
  - `confirm-once`：执行前问一次，**答案写入规则文件，之后不再问**；
  - `attended`：每次都需要人确认（用于不可逆动作）。
  `reject` 不产生修改，可省略 `mode`。
- `source`：这条规则从哪来（哪次澄清 / 哪次人工修正归纳）。缺失 `source` 的规则视为草稿，不得进入生产运行。
- `unmatched: halt`：任何未覆盖情况一律停机，严禁猜测。

## 4. 运行纪律

1. **健康路径零提问、零模型调用。** 运行只读 `rules.json`。
2. **每次运行都出报告**：处理行数、按哪条规则改了什么、待办项、人工介入次数。人工介入次数是决定"是否要找 Agent 改规则"的唯一指标。
3. **写盘前先 dry-run**：输出变更清单（原值 → 新值 x N 处），确认后才写。
4. **可追溯**：覆盖原始数据时另存修复版并保留原值列/变更日志（原值、新值、依据规则、时间）。原始记录被修改必须可自证。
5. **规则漂移检测**：每次运行读取文件中的实际阈值与 `rules.json` 比对，不一致时停机报告"规则与文件不符"，而不是继续用旧规则运行。

已实现的对应入口：

| 环节 | 命令行 | 图形界面 |
|---|---|---|
| 校验规则 | `sharingan rules validate <rules.json>` | 规则页（保存前自动校验） |
| 看数据概况 | `sharingan inspect <data.csv> --rules …` | 数据概况页 |
| dry-run | `sharingan plan <data.csv> --rules … [--json out.json]` | 变更清单页「生成变更清单」 |
| 执行写入 | `sharingan apply <data.csv> --rules … --yes` | 变更清单页「执行写入…」→ 确认对话框 |

写入一律：**先备份 → 再改数据 → 落变更日志**（原值、新值、依据规则、规则来源、时间）。
dry-run 判定为停机时，命令与界面都拒绝写盘。

## 5. 升级报告（停机时产出）

规则未覆盖或发生冲突时，输出一份可直接交给 Agent 的报告：

```json
{
  "run_id": "2026-07-31T09:12:00",
  "halted_at": "writeback",
  "reason": "unmatched_case",
  "evidence": {
    "locations": [{"row": 512, "col": "O", "value": 61.2}],
    "violated_rules": [],
    "context": "列 O 出现超过阈值但未定义修复规则"
  },
  "candidates": ["clip到限值", "按邻点插值", "人工判断"],
  "suggestion": "需要澄清：该列异常的处理方式"
}
```

Agent 拿到报告后修改 `rules.json` → 出新版本与 diff → 用历史若干周数据回归（脚本结果必须与模板/既有结论一致）→ 通过后提升版本。任何版本可回滚。

## 6. 模板核对（`sharingan template`）

分析模板（xlsx）是规则的**另一个事实来源**，而且是目前唯一会被人手工编辑的地方。
工具把它读一遍并与 `rules.json` 交叉核对，只报告不一致，不替人挑一个用：

| 检查 | 说明 | 级别 |
|---|---|---|
| 表头文字 vs 条件格式阈值 | 同一参数写在两处，可能不一致（真实模板的 T 列：20 对 25） | error |
| 规则 vs 模板阈值 | 规则里的阈值与模板（优先表头）不一致 | error |
| 规则 vs 模板派生公式 | 公式文本按统一写法比较（`=ABS(O4-J4)-4.1000` ≡ `abs(O-J)-4.1`） | error |
| 统计窗口不一致 | 各列 `MAX(…)` 的行区间不同（真实模板 K 列只到 599，其余到 1029） | warn |
| 窗口盖不住数据区 | 数据行数超过统计窗口末端，窗口外数据不参与判定 | warn |
| 公式含硬编码常量 | 如 Y 列的 `-4.1`，需确认是否有意为之 | warn |
| 条件格式多档阈值 | 如 P 列有 25 与 50 两档，取最严档作判定边界 | info |

浮点表示噪声会被抹平（Excel 把 `4.1` 存成 `4.10000000000001`，不算不一致）。

## 7. 反模式（明确禁止）

- 运行期重新弹一整套问卷；
- 问题被"跳过"而不是被解决（假静默）；
- 把规则留在提示词或聊天记录里，而不落成文件；
- 未定义的情况靠模型猜一个值写进数据；
- 静默覆盖原始数据、无备份、无变更记录；
- 在公开仓库里提交真实生产数据（见 README 的数据红线）。

## 8. 跨平台约束

项目要求 Windows / macOS / Linux 通用，因此按"核心零平台耦合、平台差异只进适配器"三层划分：

| 层 | 状态 | 规则 |
|---|---|---|
| 核心（格式读写、规则、公式、夹具、分析、生成、运行） | 已有实现 | 纯标准库；路径用 `pathlib`；换行符运行时探测；编码自动识别；禁止 `winreg` / `ctypes.windll` / `os.startfile` / 盘符路径 / `shell=True` |
| 采集层（录屏、键鼠事件、辅助功能树） | 未开始 | 只有这一层允许调用操作系统 API；按平台分文件放在 `sharingan/platforms/`，对上层暴露统一接口（`recorder` / `events` / `ui_tree`） |
| UI 层 | 已有首个版本（`sharingan/ui/`） | **PySide6（Qt for Python）**：普通用户需要真正的桌面程序（双击即用，没有浏览器、端口、防火墙的顾虑），PySide6 为 LGPL、三平台原生窗口，控件足以承载表格、截图与 diff 复核。它是**可选依赖**（`pip install "sharingan[ui]"`），核心保持零依赖；未安装时 CLI 不受影响。启动时按候选列表挑选中文字体（Windows 微软雅黑 / macOS 苹方 / Linux Noto CJK），找不到时打印安装提示。界面只渲染 `analysis` 层产出的 Summary，**自身不含任何规则判断逻辑** |

护栏：`tests/test_platform_neutrality.py` 扫描核心源码，命中平台专用写法即测试失败，防止耦合回潮。

数据与产物同样要保持可迁移：生成的文件一律使用现场既有格式（GBK + CRLF），不使用平台特有的换行或编码假设。
